# V0.2 Supabase Validation Checklist

This checklist is the release gate for the MyPersonaOS V0.2 persistence milestone.

## 1. Local automated checks

Run from a clean checkout:

```bash
npm ci
npm audit --audit-level=moderate
npx tsc --noEmit
npm run lint
npm run build
```

These checks prove that dependencies install without known audited vulnerabilities,
TypeScript compiles, lint rules pass, and Next.js can produce a production build.
They do **not** prove that Supabase RLS, Realtime, authentication, or multi-device
synchronization work.

## 2. Supabase project setup

1. Create a private Supabase project.
2. Disable public user sign-up in Authentication settings.
3. Create the single owner user.
4. Apply migrations in order:
   - `supabase/migrations/20260807000000_v0_2_schema.sql`
   - `supabase/migrations/20260807001000_v0_2_hardening.sql`
5. Configure `.env.local` from `.env.example`.
6. Restart the Next.js development server after changing environment variables.

## 3. Schema / security inspection

Verify in the Supabase dashboard or SQL editor:

- RLS is enabled for `user_profiles`, `projects`, `tasks`, `inbox_items`, `content_pieces`, and `english_words`.
- Domain policies use the authenticated user's `user_id`.
- `user_profiles` policy uses the authenticated user's `id`.
- `import_local_snapshot(jsonb)` is executable by `authenticated`, not `anon`/`PUBLIC`.
- `content_pieces.platforms` exists as `text[]`.
- `user_profiles` and all domain tables are members of `supabase_realtime`.
- `tasks.project_id` cannot reference a project owned by another user.

## 4. Legacy migration test

Use a browser profile with V0.1-style local data, including legacy IDs such as `1`, `p1`, `i1`.

Expected behavior on first private login:

1. A browser-side pre-migration backup is created.
2. Legacy entity IDs are converted to UUIDs while preserving Task -> Project and Inbox -> converted target relationships.
3. The atomic RPC imports the complete snapshot.
4. `mainFocus` and `contentPieces.platforms` survive the migration.
5. `user_profiles.migration_version` becomes `1` only after a successful import or an explicit cloud-wins decision.
6. A migration failure must leave local state visible and must not replace it with an empty cloud snapshot.

## 5. RLS isolation test

For a security test project, temporarily create two users A and B.

Verify:

- A cannot select B's rows.
- A cannot update or delete B's rows.
- A cannot insert a Task with `user_id = A` and `project_id` belonging to B.
- B cannot access A's `user_profiles.settings`.

Delete the temporary second user after the test if the production project is intended to remain single-owner.

## 6. Delete synchronization test

1. Create a Task on desktop.
2. Confirm it appears on mobile.
3. Delete it on desktop.
4. Confirm it disappears from the database and mobile without returning after reload.
5. Repeat with an Inbox item.

## 7. Offline outbox test

1. Login while online and confirm `Cloud synced`.
2. Disconnect the desktop from the network.
3. Create a Task, change Main Focus, and delete an Inbox item.
4. Reload while still offline; the local changes must remain visible.
5. Restore the network.
6. Confirm queued operations flush and the UI returns to `Cloud synced`.
7. Confirm the mobile device receives the same final state.

## 8. Realtime multi-device test

With the same owner logged in on PC and mobile:

- Quick Capture on PC appears on mobile.
- Task status changes propagate both directions.
- Main Focus changes propagate through `user_profiles` Realtime.
- Deletions propagate.
- A burst of several changes results in a final consistent state rather than repeated stale overwrites.

## 9. Auth / privacy test

- With Cloud Mode configured, unauthenticated access redirects to `/login`.
- `/login` does not render Sidebar or Global Quick Capture.
- Signing out immediately hides application data and returns to `/login`.
- Static assets, manifest, and `sw.js` are accessible without authentication.
- Direct `/login` access in Local Mode offers a Local Mode continuation instead of trying to instantiate an unconfigured Supabase client.

## Known V0.2 boundary

V0.2 uses a durable browser outbox and last-write-wins cloud updates. It does not yet implement collaborative field-level conflict resolution or encrypted browser storage. The product remains a private, single-owner system; multi-user SaaS behavior is outside this milestone.
